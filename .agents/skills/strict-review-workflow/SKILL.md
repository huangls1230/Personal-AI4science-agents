# Strict review workflow

Codex is the sole orchestrator. Select only the requested scope: **full** → Method, Statistics, Consistency, then Doublecheck and aggregation; **method**, **statistics**, or **consistency** → the corresponding specialist only; **doublecheck** → independent review then adjudication of the specified prior reports; **targeted re-review** → only affected findings, sections and dependencies on a newly hashed manuscript. Do not create another lead, modify the manuscript or submit a review. Read the applicable specialist skills in `.agents/skills/` (`methodology-review`, `statistical-review`, `consistency-review`, `scientific-doublecheck`) and the existing `teams/strict_review/` schemas and templates as needed, not all references at once.

## Intake, scope and snapshot

Establish `project_id`, authorized manuscript and type, scope, domain, evidence/data/code/figure paths, review policy and output directory. For confidential third-party submissions verify the rights-holder, venue and institutional AI policies for the actual processing environment before reading content; local scripts do not make a hosted model local. No permission means stop restricted processing. When the task falls under the installed `peer-review` workflow, comply with its intake, authorization and unchanged `READY_FOR_LOCAL_REVIEW` gate; a BLOCKED gate stops that workflow. Do not relabel a task or falsify `local_only` to bypass it. The gate does not authorize a hosted session merely because analysis scripts run locally.

Create a fresh session under `workspace/projects/<project_id>/reviews/<review_session_id>/`, using authorized files and existing workspace tools. Preserve one non-overwriting manuscript snapshot, its SHA-256, source path, start time, scope, permission status and hashed inventory; give all specialists the same snapshot/hash and separate output directories. Record each evidence item as available, partial, unavailable, restricted or not_checked, with actual path, hash and access method where applicable. Existing path checks and hashes are not OS isolation or proof of authorship. Recheck source and snapshot hashes before aggregation; report version changes and do not combine incompatible reports. Keep source and previous reports unchanged.

## Execute and verify

- Run the selected specialists on only necessary authorized source material, in parallel only when isolation and independent output paths are actually available. Do not use another reviewer’s summary as primary evidence. No data means report-level statistics only; an unread figure is not visually checked; record absent data, figures and unexecuted calculations explicitly. Execute deterministic metric calculations only on real authorized inputs; never execute untrusted code or assume reproduction from a calculation.
- Doublecheck Pass 1 receives the snapshot, relevant primary evidence and scope only; persist and hash independent findings, review and argument map before exposing other reviewers' conclusions. Pass 2 checks each major finding against primary evidence and the same manuscript version, then records adjudication, disagreements and omissions. If context or filesystem access cannot be isolated or prior conclusions were exposed, mark `blind_review: false` and describe limitations; a new prompt, role or hash alone does not prove blindness.
- Preserve every original Finding in the existing `teams/strict_review/review-finding.schema.json`; put cross-review metadata such as `originating_agent`, `source_finding_ids`, `manuscript_hash`, adjudication and unresolved questions in a separate aggregation wrapper rather than altering the strict schema. Merge duplicates only when evidence and conditions justify it, retaining all source IDs; preserve genuine unresolved conflicts. A missing or different report hash blocks direct adjudication for that report. Reviewer agreement does not establish truth.
- Verify output schema, unique IDs, referenced file hashes and locations, Major/Critical evidence, actual calculation and visual-check execution, and unchanged inputs. Validation is structural and provenance checking, not proof of scientific validity. Preserve successful artifacts if a specialist fails; label the session `partial`, not full. Distinguish `verified`, `potential`, `insufficient_information` and `not_checked`; unreported is not unperformed.
- Reuse an existing result only after checking matching manuscript and authorized evidence hashes, scope, policy, tool version, material access and validation state. Hash equality alone is not automatic approval or a cache hit. For targeted re-review bind old findings to the old hash, re-evaluate affected evidence and mark closure only after actual verification and human decision.

## Delivery

Save `input_manifest.json`, role-specific outputs, `aggregated_findings.json`, `strict_review_report.md`, `review_validation.json` and `execution_manifest.json` in the session; retain the project Task / Result Contract and workspace-relative evidence references. The report distinguishes strengths, severity, supported and disputed concerns, author actions, unverified or unavailable material, and human approval. Pass only approved finding IDs and evidence to manuscript editing when the user requests it; editing produces a new version and does not automatically close findings.

Record actual role calls (`native_subagent` only with a real selected-role event; otherwise `inline_skill`), deterministic tool runs, blind-review evidence and unknown usage/cost as unknown. Metadata discovery and successful validation do not prove role execution or scientific correctness. The result is an accountable draft, not a journal decision.
